# Sparse, annealed level supervision for NCM on Sudoku

Status on 2026-11-01: pilot only, one seed. Runs A, B, F, G, H and I are complete; E and J are still running. C and D have not been run.

## Summary

- No supervision variant has beaten the baseline. At 2400 updates, baseline A solves 76.70% of easy boards and the best variant, G, solves 61.95%.
- Reducing the loss of supervision helps: F, G and I all beat B, the first sparse variant.
- Masking only the fine levels (H) scored below B, even though it keeps more supervision. This is unexplained.
- These pilots stop at 2400 of the paper's 50k updates, so they show early training behaviour, not final performance.
- E and J are the remaining test. They train the token loss on the model's own codes, which targets B's main failure: token CE reached 0.02 during training while free-running generation still failed.

## Question

Can NCM train with sparse parent-child level supervision, annealed over time, plus an end-to-end token loss, and match or beat full level supervision?

The loss is:

```
L = e2e_weight * L_token + lambda(t) * sum_k m_k * w_k * CE_k
```

- `CE_k` is the code cross-entropy at level k, with weight `w_k = l_k^-alpha / sum_j l_j^(1-alpha)`.
- `m_k` is the mask. `level_mask_prob` is the probability of dropping a level's supervision.
- `lambda(t)` is the guidance schedule.
- `L_token = CE(D(z_hat), solution)` passes through the frozen tokenizer decoder, using Gumbel-softmax codes (tau 1.0).

The tokenizer weights are never changed. All new behaviour sits behind flags that default off.

## Setup

The repo ships inference code only, so the trainer ([train.py](../train.py)) and training-board generator ([gen_sudoku.py](../scripts/gen_sudoku.py)) are our reconstruction. Run A is therefore not a bit-for-bit reproduction of the authors' training.

| Item | Pilot value | Source |
|---|---|---|
| Updates | 2400, fitted to a 3 h budget | ours |
| Effective batch | 256: 128 x 2, or 64 x 4 for rollout | paper uses 1024 |
| Learning rate | 3e-4 to 3e-5, cosine | paper |
| Warmup | 240 updates (`min(1000, steps // 10)`) | paper uses 1000 for 50k updates |
| Optimizer | AdamW, betas (0.9, 0.99), weight decay 0.01, clip 1.0 | paper |
| `alpha` | 1 | inferred, not given for Sudoku |
| Corruption | linear 0.75 to 0.25 across levels | inferred, not given for Sudoku |
| Tokenizer | released `sudoku/medium`, frozen | released |
| Training boards | 20k generated grids with unique-solution nested clue sets (40/35/30), excluding test grids, with symmetry augmentation | ours |
| Training difficulties | easy and medium | ours |
| Test boards | released easy, medium and hard | released |
| Hardware | Kaggle, 2 x T4, one run per GPU, fp16 | |

A T4's 14.56 GB cannot hold micro-batch 256, which is why these runs use gradient accumulation.

## Checks

- Baseline `generate` output hashes for the released checkpoints are unchanged by this work.
- The released hard model solves 86.3% of 2000 hard boards, against 86.1% in the paper.
- The released medium model solves 96.4% of 384 boards from our generated pool, against about 96.5% expected.
- [test_training.py](../tests/test_training.py) passes all 7 checks. They include the baseline loss matching Eq. 10, no gradients reaching the tokenizer, and exact resume after a crash.
- A T4 smoke run with all features on passed, including a hard kill and resume.

## Limitations

- Each run has one seed.
- Pilots use about 5% of the paper's updates and a quarter of its batch size.
- All runs share a step count, so the comparison is at equal updates. Variants with a token loss take longer per update: about 3.75 s for B against 2.97 s for A.
- `alpha` and the corruption schedule are inferred, and may favour or penalise some variants.
